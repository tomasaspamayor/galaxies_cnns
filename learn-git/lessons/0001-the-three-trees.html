The Three Trees: how Git actually thinks

One mental model that makes every other Git command predictable.

~12 minutes Skill: control exactly what goes into a commit Prerequisite: add · commit
Why this, for your project

You want to manage your galaxies analysis confidently. The reason Git feels mysterious is that most people never learn where their changes live. Once you can picture the three places a change can sit, "what will git commit actually record?" stops being a guess — and your experiment history stays trustworthy.

Git keeps three copies of your project

This is the whole idea. A working Git repository is really three separate places your files can exist:

Working tree

The files you actually edit — your analysis.py, your notebook, your data. Just a normal folder.

Staging area

A holding pen for the next commit. Its technical name is the index. This is where you choose what to record.

Git directory

The permanent database of snapshots — the .git folder. Committed work lives here forever.

edit a file  →  git add  →  staging area  →  git commit  →  git directory

Every file in your project is in one of three states, named after those places (Pro Git §1.3):

  • Modified — you changed it in the working tree, Git hasn't recorded it yet.
  • Staged — you marked this exact version to go into the next commit.
  • Committed — it is safely in the git directory.
The key misconception

git add does not "add a file to the project". It copies the file's current content into the staging area. If you edit the file again afterwards, the working tree has newer changes the staging area doesn't know about — so the same file can be both staged and modified. This trips up almost everyone at first.

And one more pointer you'll see constantly: HEAD. HEAD is just a marker for "where you are right now" — normally the branch you're on, and therefore the last commit you built on top of.

Skill 1 · Read git status like a scientist

git status tells you which of the three places each change is in. The full output is wordy; the short version is a precise two-column code. Run:

$ git status -s
 M analysis.py
M  results.csv
MM notebook.ipynb
?? raw_data/

Read it as two columns: the left column is the staging area, the right column is the working tree.

CodeLeft (staged)Right (working tree)Meaning
MspaceMModified, not staged
M MspaceModified and staged
MMMMStaged, then edited again
????Untracked — Git has never seen it

The blank space is information: it means "nothing here". So M and M are different situations, and now you can tell them apart.

Skill 2 · See the actual lines with git diff

git status names files; git diff shows the exact lines added and removed. There are two flavours, and beginners mix them up constantly:

# working tree  ⇄  staging area   (what you changed, not yet staged)
$ git diff

# staging area  ⇄  last commit    (what will go into the next commit)
$ git diff --staged

If you've staged everything and run plain git diff, it prints nothing — because there's no unstaged change left. That empty output is correct, not a bug.

Skill 3 · Undo precisely, without losing work

Because you now know the three places, you can move changes between them on purpose. Two commands do almost all of it (Pro Git §2.4):

# Un-stage a file (move it back to the working tree). Your edits are KEPT.
$ git restore --staged analysis.py

# DISCARD working-tree edits, reverting the file to the last commit.
# DANGEROUS: your unsaved edits to that file are gone for good.
$ git restore analysis.py
Memory hook

--staged means "reach into the staging area". Without it, restore reaches into your files. Committed work is almost always recoverable; uncommitted work that you restore away is not.

Check yourself

Click an answer on each question. You get feedback immediately — and only one try, so answer from memory.

Question 1You edit analysis.py and run no Git command. Where does the change live?

Why: Editing only touches the working tree. Nothing reaches the staging area until you run git add.

Question 2git status -s shows  M analysis.py (a space, then M). What is the state?

Why: The left column (staged) is blank; the right column (working tree) shows M. It's modified but not staged.

Question 3Which command shows the exact lines you changed that are not yet staged?

Why: Plain git diff compares working tree to staging area. --staged compares staging area to the last commit. log looks at history, not your pending edits.

Question 4You staged junk.py by mistake but want to keep your edits on disk. What do you run?

Why: --staged un-stages while keeping your edits. Bare git restore junk.py would delete your edits.

Question 5After git commit succeeds, where does that snapshot live?

Why: A commit writes the staged snapshot into the git directory, where it becomes permanent history.

Practice on your own repo

Do this in your learn-git or galaxies_cnns folder. The point is to predict the result before running each command.

  1. Run git status -s. For each line, say out loud which column has a letter, and what that means. Predict first, then check.
  2. Pick a tracked file you don't mind touching. Add a blank line, save, and run git status -s. You should see  M — unstaged.
  3. Run git diff. Confirm your blank line is shown as an addition. Then run git diff --staged and confirm it shows nothing.
  4. Run git add <file>, then git status -s. The code should flip to M . Run git diff (now empty) and git diff --staged (now shows your line).
  5. Undo the staging with git restore --staged <file>. Confirm with git status -s that it's back to  M and your blank line is still in the file.
  6. Discard the experiment for good: git restore <file>, then git status — clean again.

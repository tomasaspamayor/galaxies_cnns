Git for your research project · Lesson 0002

Branches are just pointers

Try a risky idea, keep the good one, and never touch your working version.

~15 minutes Skill: isolate an experiment, then merge it back Builds on Lesson 0001
Why this, for your project

You want to try a new model architecture or a different data-cleaning step without risking the analysis that already works. That is exactly what branching is for. Once you see that a branch is a disposable pointer, "let me just try this" stops being scary.

A branch is a label on a commit

In Lesson 0001 you learned that a commit is a snapshot, and that each commit points back to its parent. So your history is a chain:

C0 ◄── C1 ◄── C2        # each commit points to its parent

A branch is nothing more than a movable pointer to one of those commits — a 41-byte file holding a commit's hash (Pro Git §3.1). When you commit, the branch you're on slides forward to the new commit. That's it. There is no "copy of the project" anywhere.

Branch

A movable pointer that follows you as you commit.

Tag

A fixed label that never moves (Lesson 0004).

HEAD

A pointer to the branch you are currently on.

HEAD is the answer to "where am I?". It normally points at a branch, not at a commit directly. When HEAD moves, your working tree changes to match — which is the next key idea.

The surprising part

Switching branches rewrites your files. Git adds, removes, and modifies files so your working tree matches the branch you switched to (Pro Git §3.2). If you have uncommitted changes that would be clobbered, Git refuses the switch to protect you. Commit or stash first.

The commands

# create a branch AND switch to it
$ git switch -c experiment

# list branches (the star marks your current one)
$ git branch

# move between branches
$ git switch main
$ git switch -            # jump back to the previous branch

# see the shape of history as a graph
$ git log --oneline --graph --all

git checkout -b x is the older spelling of git switch -c x. You'll meet both in the wild.

Divergence: two lines from one point

Branch, commit on the branch, switch back, and commit again — now history has diverged. Both lines share a common ancestor commit:

              ┌── C3 ◄── experiment
C0 ◄── C1 ◄── C2
              └── C4 ◄── main

Nothing on experiment has touched main. You can switch between them freely; your working files follow. This is the whole safety mechanism.

Bringing work back: merge

git merge <branch> combines another branch into the one you're on. Git picks one of two modes:

ModeWhenResult
Fast-forwardYour branch is a direct ancestor of the otherPointer slides forward. No new commit.
Three-way mergeBoth branches have divergedA new merge commit with two parents.
 
$ git switch main
$ git merge experiment

When both sides touch the same line

If the two branches changed the same lines, Git can't guess and stops with a merge conflict. It writes markers into the file:

<<<<<<< HEAD
your current branch's version
=======
the incoming branch's version
>>>>>>> experiment

To resolve: edit the file to the result you actually want, delete the three marker lines, then git add the file (staging marks it resolved) and git commit. To abandon the merge entirely, run git merge --abort.

Question 1What is a branch, really?

      
      
      
      
Why: A branch is just a reference to one
      commit. That is why creating one is instantaneous and costs almost nothing.

    


    

      
Question 2You run git switch -c experiment and make a commit. Where does main point now?

      
      
      
      
Why: Committing moves only the branch you
      are on (experiment). main stays put until you merge.

    


    

      
Question 3When does a merge produce no new commit (a fast-forward)?

      
      
      
      
Why: With no divergence there is nothing to
      combine, so Git just slides the pointer forward.

    


    

      
Question 4In a conflict, the text written above the ======= line is whose version?

      
      
      
      
Why: The top block is what HEAD
      (the branch you're merging into) contains; the bottom block is the branch
      being merged in.

    


    

      
Question 5You've edited a conflicted file to the resolution you want. What next?

      
      
      
      
Why: git add marks the file as
      resolved, then git commit finalises the merge commit.

    

  


  
Practice on your own repo

  
Use learn-git. Predict each result before running it.

  
    
    
  1. Run git switch -c practice-branch. Confirm with
    git branch that you're on it (star). Run git status —
    the working tree is unchanged.
    2. 
    
  2. Make a tiny edit to any file and commit it. Run
    git log --oneline --graph --all — your branch is ahead.
    3. 
    
  3. Run git switch - to jump back. The file you edited reverts to how
    main had it — proof that switching rewrites your files.
    4. 
    
  4. Merge it: git switch <original-branch> then
    git merge practice-branch. It should fast-forward
    (no commit made on the original branch in between).
    5. 
    
  5. Clean up: git branch -d practice-branch. History is preserved.
    6.
